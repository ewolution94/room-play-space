# Codebase Audit — Room Play Space

Full pass over the app (types, state, 2D canvas, 3D view, multi-room view, sidebar/inspector, lib utilities, routes, persistence, tests) looking for bugs, cross-view inconsistencies (this was built by three different agents across many sessions), and UX opportunities. Ordered roughly by how much it matters.

> **Status update (follow-up session):** Sections 1 and 2 are now fully fixed. Section 6's "Quick wins" are fixed except one (flagged below). Test coverage gaps from section 4 have been closed for the pure-function modules; component/hook-level tests are still missing. Section 3 has one item fixed (door/window validation, duplicated from the quick wins list) — the rest, and all of section 5 (Accessibility) and section 6's Medium/Bigger swings, are still open and now tracked as the actionable backlog in `todo.md` so there's one place to look for what's next.

## 1. Confirmed bugs — ✅ all fixed

**✅ Fixed — "Enable Collision" doesn't actually disable collision everywhere (single-room view).** `collidesWithOthers()` in `planner-math.ts` takes a `collisionEnabled` parameter that defaults to `true`. The mouse-drag path in `use-room-planner.ts` explicitly wraps its collision check in `if (collisionEnabled)`, so dragging respects the toggle. But `updateItem` (used by every Inspector number field), the arrow-key nudge, and the "R" rotate-in-place keyboard shortcut all call `collidesWithOthers` with no third argument, so they silently enforce collision *regardless of the checkbox*. Concretely: turn off "Enable Collision," drag one couch on top of another with the mouse — works. Nudge it 1px further with an arrow key, or type a new X coordinate in the Inspector — silently rejected, with zero feedback (no toast, the field just snaps back). Worth deciding whether collision-off should mean "off, full stop" and threading the flag through consistently, or renaming the toggle to something narrower.
&nbsp;&nbsp;→ *Fix: every call site (`updateItem`, arrow-nudge, "R" rotate) now passes `collisionEnabled` through.*

**✅ Fixed — Dragged item snaps back on release even with collision disabled.** Related to the above but distinct: in `onStagePointerUp` (`use-room-planner.ts`), the post-drop collision re-check that decides whether to revert a drag to its start position *also* doesn't pass `collisionEnabled`. So with collision off, you can drag a piece of furniture into an overlapping position and watch it happily overlap during the drag — then the moment you release the mouse, it snaps back to where it started, as if collision were still on. This is very reproducible and probably the single most confusing bug in the app, because it looks like the checkbox does nothing.
&nbsp;&nbsp;→ *Fix: same `collisionEnabled` threading fix as above covers the post-drop revert check.*

**✅ Fixed — The multi-room view has no undo, at all.** The single-room planner has full undo/redo (Ctrl+Z, 100 steps, keyboard shortcuts, header buttons). `MultiRoomCanvas.tsx` has none of that machinery — no `pushHistory`, no history stack, nothing. Dragging a room, resizing it, rotating it, or clicking "Delete" on a room (which also deletes every item/opening inside it) cannot be undone. There's also no confirmation dialog before deleting a room, unlike the single-room "Reset" flow, which does confirm. This is the biggest asymmetry in the app between its two main surfaces, and the one most likely to genuinely lose someone's work.
&nbsp;&nbsp;→ *Fix: ported the single-room `historyRef`/`futureRef` pattern into `rooms.index.tsx`, scoped to the active floor's rooms (cleared on floor switch). Ctrl+Z/Shift+Z/Y plus header Undo/Redo buttons now work in the multi-room view too. The confirm-before-delete dialog was added separately and stays even with undo available.*

**✅ Fixed — Opening's wall label breaks for hallway (polygon) rooms in the Elements list.** `ElementsListSection.tsx` renders an opening's wall as `t[o.wall]`. For a plain rectangular room `o.wall` is `"top"/"right"/"bottom"/"left"` and this works. For an L/T-shaped hallway, `o.wall` is a *number* (wall index) — `t[o.wall]` is `undefined`, so the row silently renders "Door · · 120cm" with a blank gap where the wall name should be. `InspectorSection.tsx` already has a `wallLabel()` helper that handles this correctly (falls back to "Wall N" for numeric walls); `ElementsListSection.tsx` just doesn't use it. Easy fix, but worth promoting `wallLabel` to a shared lib function (e.g. `hallway-shapes.ts`) so it can't drift again.
&nbsp;&nbsp;→ *Fix: `wallLabel()` promoted to `hallway-shapes.ts`, both components now import the shared version. Covered by new tests in `tests/hallway-shapes.test.ts`.*

**✅ Fixed — Arrow keys in the 3D view hijack the range sliders.** `ThreeDView.tsx` has a global `keydown` listener for panning the camera with arrow keys, with no check on `e.target`. Focus the "Sunlight Angle" (or wall-fade) slider in the 3D view controls panel and press ArrowLeft/Right expecting the native slider behavior — instead the camera pans, and `e.preventDefault()` blocks the slider's own arrow-key handling entirely. The single-room 2D keyboard handler in `use-room-planner.ts` does guard against focused inputs; this one doesn't.
&nbsp;&nbsp;→ *Fix: added the same focused-input guard (input/textarea/select/contentEditable) to `ThreeDView.tsx`'s camera-pan listener.*

**✅ Fixed — Multi-floor/multi-room import has none of the single-room import's safety checks.** Single-room import (`planner-schema.ts`) validates through zod: numeric bounds on every field, a regex on color strings, and hard caps (1000 items, 200 openings) explicitly "to prevent tab freezing." The multi-floor import path (`parseImportedFloors` in `floors.ts`) does a shallow structural check only (`typeof r.id === "string" && "width" in r && "x" in r`) — no bounds, no color validation, no item/room count cap. A malformed or hostile JSON file imported via the `/rooms` Import dialog could set absurd coordinates, invalid colors, or tens of thousands of items with no guardrail at all. Worth reusing/extending the same zod schema for the floors import path.
&nbsp;&nbsp;→ *Fix: added `roomLayoutSchema`/`floorSchema`/`floorsArrayImportSchema`/`roomLayoutArrayImportSchema` to `planner-schema.ts`, mirroring the single-room schema's bounds/caps/color regex (plus a 100-floor, 500-room cap). `parseImportedFloors` now validates through these instead of the shallow structural check. Covered by new tests in `tests/planner-schema.test.ts`.*

## 2. Cross-view inconsistencies (the "three agents" seams) — ✅ all fixed

A few patterns show up in exactly one of the two main views and not the other, which is the clearest fingerprint of different agents/sessions building each side:

- **✅ Fixed** — Keyboard arrow-nudge in the multi-room view correctly respects `collisionEnabled` and correctly ignores keystrokes while an input/textarea/select is focused. The single-room equivalent does neither (see bugs above). The multi-room one is the better-written of the two — worth back-porting its pattern into `use-room-planner.ts` rather than the other way around.
  &nbsp;&nbsp;→ *On inspection, `use-room-planner.ts`'s keyboard handler already had the focused-input guard; the collision-toggle threading was the actual gap, fixed above.*
- **✅ Fixed** — `lang` is passed down as an explicit typed prop (`"en" | "de"`) almost everywhere — `Sidebar`, `MultiRoomCanvas`, `MultiRoomInspector`, `ThreeDView`'s own prop shape elsewhere — except `CanvasArea.tsx`, which instead *derives* it via `t.title === "Raumplaner" ? "de" : "en"`. The exact same string-comparison hack is duplicated independently in `HintBanner.tsx` and `ThreeDView.tsx` (`const isDe = t.title === "Raumplaner"`). It works today only because nobody has changed that one German string. The moment the app's title copy changes, every `lang === "de"` conditional fed by this derivation silently breaks and falls back to English. `CanvasAreaProps` doesn't even declare a `lang` field — it should, matching every sibling component.
  &nbsp;&nbsp;→ *Fix: `lang` is now a real threaded prop through `CanvasArea` → `HintBanner`/`ThreeDView`; the string-sniffing hack is gone from all three files.*
- **✅ Fixed** — The single-room Reset flow shows a confirmation dialog; deleting an entire room (with everything in it) in the multi-room view does not.
  &nbsp;&nbsp;→ *Fix: added an `AlertDialog` confirm step to `MultiRoomCanvas.tsx`'s single and bulk room deletion, mirroring the single-room Reset flow.*
- **✅ Fixed** — `Sidebar.tsx` receives `wallColors`/`setWallColors`/`flooring`/`setFlooring` as props (threaded all the way from the route) but never uses any of them — that UI actually lives in the floating `InspectorSection`. Harmless, but it's dead prop-drilling that makes the component's real dependencies harder to read.
  &nbsp;&nbsp;→ *Fix: removed from `SidebarProps`, `Sidebar.tsx`'s destructuring, and both route call sites — `setCorners` turned out to be equally dead and was removed the same way.*

## 3. Other risks worth a look

- **✅ Fixed — No bounds/overlap validation when adding a door or window.** `OpeningsDialog` lets you type any position/width with only a `min`, no `max` tied to the wall's actual length, and `addOpening()` never checks against the wall length or against other openings already on that wall. You can place a door that hangs off the end of a wall or two overlapping doors on the same wall; nothing stops it or warns about it.
  &nbsp;&nbsp;→ *Fix: `addOpening` and `updateOpening` (in `use-room-planner.ts`) now reject placements that don't fit the wall's real length or overlap an existing opening on that wall, with a toast (`t.openingOutOfBounds`/`t.openingOverlap`).*
- ⏳ **Open — Unseeded texture noise in the 3D view.** `floor-materials.ts`/`floor-pattern-geometry.ts` went out of their way to use a seeded `mulberry32` PRNG specifically so wood grain/carpet fleck patterns stay stable across renders instead of "jittering" — the comments are explicit about this. `ThreeDView.tsx`'s `createProceduralTexture` (used for furniture materials: wood/fabric/leather/plant/rug/stone) uses plain `Math.random()` with no caching, and the file's own scene-rebuild effect fires on almost any state change (moving one item, changing selection, toggling dark mode). Net effect: every wood-textured desk/table in the room silently gets a freshly-randomized grain pattern on every rebuild — the exact "jittery = broken-looking" problem the floor code was written to avoid, just not caught here. Worth either caching per (material, color) like the kit-model tinting already does, or seeding it. *(Tracked in `todo.md`.)*
- ⏳ **Open — `readableText()` (used to pick black/white label text on a colored swatch) only handles 6-digit hex.** The import schema explicitly allows 3/4/8-digit hex colors; any of those imported would silently fall back to black text regardless of actual brightness. Minor, but a real gap between what the schema accepts and what the color utilities support. *(Tracked in `todo.md`.)*
- ⏳ **Open — History snapshots are full deep clones (`JSON.parse(JSON.stringify(...))`) on every `pushHistory` call**, capped at 100 entries. Fine at normal furniture counts; the multi-floor import path now caps item/room counts (see section 1), which bounds the worst case, but a very large hand-built floor plan could still make every single drag noticeably slower. Multi-room undo (now added) uses the same deep-clone pattern for its own `RoomLayout[]` snapshots, so this applies there too. *(Tracked in `todo.md`.)*
- ⏳ **Open — A handful of `catch {}` / `catch (err) {}` blocks around `releasePointerCapture` calls swallow errors silently** (low risk — pointer capture failures are usually harmless — but worth a comment explaining why, or a `// intentionally ignored` note, so the next person doesn't wonder). *(Tracked in `todo.md`.)*

## 4. Test coverage — mostly closed

All ~3,200 lines of tests were pure-function/data-transformation tests — `planner-math`, `hallway-shapes`, `room-adjacency`, `multi-room-actions`, `planner-presets`, `default-apartment`/`default-office`, `kit-models`, `procedural-models`, `floors`, `export-filename`. That's genuinely solid coverage of the geometry/collision/catalog logic, and it's why refactors in this session kept passing consistently.

**✅ Fixed** — `floor-materials.ts`, `floor-pattern-geometry.ts`, `planner-schema.ts`, and `wallLabel` (in `hallway-shapes.ts`) previously had zero test coverage; all four now have dedicated test files/blocks (`tests/floor-materials.test.ts`, `tests/floor-pattern-geometry.test.ts`, `tests/planner-schema.test.ts`, the `wallLabel` describe block in `tests/hallway-shapes.test.ts`) covering fallback behavior, bounds/caps rejection, determinism, and the numeric-vs-named wall label split. Total suite is now 382 tests (was 318).

⏳ **Still open** — `floor-pattern-svg.tsx`/`floor-textures.ts` (the actual renderers, as opposed to the shared geometry they consume) still have no tests, and — bigger picture — there are still no component or hook tests whatsoever. `use-room-planner.ts` (1,400+ lines, all the drag/collision/undo/import state) and every React component are only ever exercised by hand. *(Tracked in `todo.md`.)*

## 5. Accessibility — ⏳ open, not addressed this pass

Checkbox/label pairing is done correctly throughout (`<label><input/><span></label>`), which covers a lot of ground for free. Past that, accessibility is thin: only 4 of roughly 25 planner-specific components use `aria-label` at all, icon-only buttons mostly rely on `title` tooltips (not reliably announced by screen readers, not available at all on touch), and there's no visible keyboard-only path to reposition the floating Inspector panels (pointer-drag only) — though item/room nudging by arrow key is a nice exception. Given the stated emphasis on UX, this is worth a dedicated pass at some point, even a light one: `aria-label` on every icon-only button, and `aria-pressed`/`aria-checked` where a toggle button currently only communicates state via color. *(Tracked in `todo.md`.)*

## 6. UX / feature ideas

Roughly ordered small → large. Anything still open here is also listed in `todo.md`, which is now the single place tracking what's actionable next — this section stays as the reasoning/context behind each idea.

**Quick wins**
- **✅ Fixed** — Fix the collision-toggle inconsistency above — this alone would remove the single most confusing interaction in the app.
- **✅ Fixed** — Add a toast when `updateItem`'s collision check silently rejects an edit ("Can't move there — overlaps another item"), instead of a field just quietly reverting with no explanation.
- **✅ Fixed** — Add the same confirm-before-delete pattern the single-room Reset flow already has to the multi-room "Delete Room" button — it's one `AlertDialog`, and it's the cheapest way to de-risk the missing-undo problem until undo itself gets built.
- **✅ Fixed** — Clamp/validate door and window placement against the wall's real length and against siblings already on that wall, with a toast on rejection (mirrors `noFreeSpace` for furniture).
- **Decided against (2026-07-27)** — Surface the "3D model color overridden" reset affordance more (e.g. a small note in the catalog itself for kit-model items). The existing Inspector banner + one-click Reset, shown after tinting, was judged sufficient — not worth the added catalog clutter.

**Medium**
- **✅ Fixed** — Undo/redo for the multi-room view. Given the single-room hook's `historyRef`/`futureRef` pattern already exists and works well, this is mostly porting it over (snapshot = `RoomLayout[]`, same push/undo/redo mechanics) rather than designing something new. *(Originally listed as "Medium" here but addressed as part of section 1's confirmed bugs, since it was the biggest asymmetry between the two views.)*
- A "snap to grid / snap to wall / snap to other furniture" magnetic-alignment mode — already on your own `todo.md` wishlist ("Smart Snapping & Collision System") and a natural companion to the ruler tool that already exists. Even just snapping rotation to 15°/45° increments and position to the nearest 5cm while a modifier key is held would go a long way for tidy layouts without a full physics-style snap system.
- A lightweight measurements/shopping-list export — a plain list of every placed item with its dimensions (you already compute exactly this for the export JSON's summary lines) as a printable/copyable list, useful when someone's actually about to go buy furniture based on a layout they made here.
- Tablet support: the mobile "view-only" cutoff is a flat 1024px window width, which catches real tablets (an iPad in portrait, or a smaller iPad even in landscape) into the stripped-down look-only mode, even though touch-drag already works fine elsewhere in the app. Worth a middle tier — full editing tools, but touch-sized hit targets — rather than collapsing straight to view-only below the same breakpoint used for phones.
- A "compare materials" or "try before you commit" affordance for flooring/wall colors — since both already render live in 2D and 3D, a quick side-by-side swatch preview (like the existing swatch grid, but showing the *actual room* thumbnail per option on hover) would make picking a floor material much less trial-and-error.

**Bigger swings**
- Real point-in-polygon furniture clamping for hallway rooms. `clampPos()` currently clamps to the hallway's bounding box, not its actual L/T silhouette — documented as a deliberate simplification, but it means furniture can end up placed in the "notch" that isn't really floor. Given hallways are a first-class room type now, tightening this would remove one of the few remaining places where a hallway behaves differently from a "real" room.
- PDF/blueprint export (also already on your wishlist) — you have precise wall/opening/furniture geometry already; a print-ready top-down floor plan with a legend and dimensions is a very natural "share this with a contractor/landlord" feature that nothing else in the app currently offers.
- A basic "before you buy" cost estimate — since presets already carry real-world dimensions and (for Kenney-backed ones) realistic proportions, attaching a rough price range per catalog item would turn this from a pure layout tool into something that helps with an actual purchase decision, which seems to be the spirit of the app already (a "room play space").

## 7. What's genuinely good

Worth saying plainly since the audit reads bug-heavy by nature: the floor-plan geometry layer (`hallway-shapes.ts`, `room-adjacency.ts`, the rectilinear-polygon collision math) is careful, well-tested, and clearly iterated on hard — that's real engineering, not just glue code. `ThreeDView.tsx`'s comments are some of the best in the codebase (camera-state preservation across rebuilds, the separate lighting effect to avoid full scene rebuilds, the z-fighting fix history) and the Kenney kit-model caching/tinting system is genuinely clever. The mobile view-only mode and its breakpoint reasoning is thought through carefully, not bolted on. None of the bugs above are architectural — they're all local, fixable inconsistencies in an otherwise coherent app.
